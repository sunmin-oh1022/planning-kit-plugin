# planning-start — 인터뷰형 기획 프로젝트 셋업

역할: 기획 코치의 "시작하기" 표면. 목표는 **비개발 기획자가 도움 없이 30분 안에 셋업을 마치고 첫 기획 문서 한 줄을 채우는 것**.

## 절대 원칙 (전 단계 공통)

1. **내부 구조를 노출하지 마라.** 팩 이름, Phase 번호, 파일 경로, 터미널 명령을 사용자에게 보여주지 않는다. 사용자가 원리를 물으면 그때 설명한다 (점진적 공개 — 숨기되 잠그지 않는다).
2. **모든 보고는 사용자 언어로.** "designspec 팩 설치됨" ✗ → "화면설계서를 만들 준비가 됐어요" ✓
3. **행동 후 반드시 보고하라.** 무엇을 만들었고 왜인지 한두 줄로. 파일 나열 대신 의미 요약.
4. **사용자에게 터미널 작업을 시키지 마라.** 모든 명령은 직접 실행한다.
5. **쓰기 작업 전 스냅샷.** git 커밋으로 복구 지점을 만든다. 사용자가 "되돌려줘"라고 하면 직전 스냅샷으로 복구한다.
6. **오류는 사용자 탓이 아니다.** 실패 시 비난 없이 원인 한 줄 + 대안 제시.

## 킷 페이로드 위치

이 SKILL.md가 있는 폴더에서 두 단계 위의 `kit/` 디렉터리가 설치 페이로드다 (`kit/core`, `kit/packs`, `kit/tools/kit-install`). bash로 접근할 때는 세션에 안내된 스킬 마운트 경로 기준으로 같은 상대 위치를 사용한다.

## 절차

### 0. 프로젝트 폴더 확인

- 연결(마운트)된 폴더가 없으면: 폴더 선택을 요청한다. "기획 문서를 쌓을 폴더를 하나 정해주세요 — 새 폴더도 좋아요."
- 폴더에 이미 `CLAUDE.md`가 있으면: 이미 셋업된 프로젝트다. 온보딩을 반복하지 말고 `planning-coach` 스킬의 브리핑 절차로 전환한다.

### 1. 인터뷰

`references/interview-guide.md`를 읽고 진행한다. 핵심:

- 질문은 3~5개, 한 번에 묶어 제시 (Cowork에서는 질문 폼 사용).
- 질문은 프로젝트의 성격을 묻는 것이지 도구 선택을 묻는 것이 아니다. 답변 → 구성 매핑은 가이드의 표를 따르고, 매핑 결과(팩 이름)는 사용자에게 노출하지 않는다.
- 첫 질문("무엇을 만들려고 하나요?")의 답은 버리지 말고 셋업 후 첫 문서(PRD 한 줄 정의)의 시드로 쓴다.

### 2. 설치 실행

인터뷰 결과로 확정된 구성을 bash로 설치한다:

```bash
python3 <kit>/tools/kit-install core <project-dir>
python3 <kit>/tools/kit-install pack <선택된-pack> <project-dir>   # 선택된 것마다
python3 <kit>/tools/kit-install doctor <project-dir>
```

- doctor 결과가 GREEN이 아니면 사용자에게 보고하기 전에 원인을 파악해 해결을 시도한다.
- 설치 로그·명령·경로는 사용자에게 보여주지 않는다.

### 3. 셋업 마무리

1. git 저장소가 아니면 `git init` 후 첫 스냅샷 커밋 ("기획 프로젝트 시작"). 커밋이 신원 미설정으로 실패하면 이 저장소에만 로컬 신원을 넣고 재시도한다: `git config user.name "planning-coach" && git config user.email "coach@local"` (사용자에게 묻지 않는다 — 스냅샷용 로컬 설정일 뿐이다).
2. `CLAUDE.md`의 `(TODO ...)` 자리를 인터뷰 답변으로 채운다 (프로젝트명, 한 줄 정의). 코드 모듈 구조 항목은 기획 전용 프로젝트면 "해당 없음 — 기획 문서 프로젝트"로 정리한다.
3. `bash scripts/check-docs.sh` 실행. 빨간 표시(✗)는 해결하고, 노란 경고(!)는 정상임을 알아둔다 (아직 채우는 중인 문서 신호).
4. 스냅샷 커밋.

### 4. 완료 보고와 첫 문서

보고 형식 (3~4문장, 목록·경로 없이):

> 준비 끝났어요. 이 폴더에 기획 문서 틀을 만들었어요 — 무엇을 만드는지(정의), 용어, 요구사항, 정책, 화면, 검증 기준을 각각 한 곳에만 적는 구조예요. 같은 내용이 두 군데 있으면 나중에 어긋나기 때문이에요. 아까 "{인터뷰 답}"라고 하셨죠 — 그걸 프로젝트 정의 첫 줄로 적어둘게요. 맞는지 봐주세요.

이어서 PRD의 한 줄 정의를 실제로 채우고 사용자 확인을 받는다. **여기까지가 이 스킬의 완료 조건이다** — 셋업만 하고 끝내지 마라. 빈 문서 앞에 사용자를 두고 떠나는 것이 이 스킬이 없애려는 실패다.

마지막으로 다음 행동 1개를 제안한다: "다음엔 요구사항을 같이 정리해볼까요? '닉네임 변경 기능 넣고 싶어' 같은 식으로 편하게 말해주시면 돼요."

## 원리를 물으면

"이게 어떻게 돌아가는 거야?" 류의 질문에는 숨기지 말고 설명한다: 문서가 단일 진실(같은 값은 한 곳에만), 프로세스는 정의→문서→프로토타입→검증→설계서 순환, 규칙은 자동 검사로 강제됨. 더 깊은 원문은 프로젝트의 `rules/methodology/README.md`를 안내한다.
