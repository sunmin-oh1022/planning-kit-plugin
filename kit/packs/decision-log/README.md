# packs/decision-log — 의사결정 추적 팩

> 진행 중 쏟아지는 회의록·일정 변경·논의 기록에서 **결정 상태의 단일 진실**을 유지한다.
> 원본(회의록)과 상태(결정 로그)를 분리 — 관리 행위는 "파일 저장 + 결정 반영 한 마디"로 끝.

## 이 팩이 필요한 경우

- 결정 기록이 회의록 추적표·POL/REQ 본문·검토 로그·로드맵에 흩어져 어느 게 최신인지 모르겠다
- 결정이 났는데 대시보드·보고서가 그걸 모르고 계속 "미결"로 표시한다 (실제 사례: 결정 후 2주 지연)
- 회의록마다 만든 "결정 추적표"가 빈 채로 방치된다
- 미결 항목에 결정권자·기한이 없어 계속 표류한다

## 무엇이 들어 있나

| 경로 | 내용 |
| --- | --- |
| `docs/DECISIONS.md` | 결정 로그 템플릿 — 한 결정 = 한 행(ID·상태·P·내부/외부·결정권자·기한·근거). **상태의 단일 진실** |
| `docs/meetings/` | 회의록·논의 기록 **불변 원본** 보관소 (`YYYY-MM-DD_제목.md`, 수정 금지·추기만) |
| `.claude/skills/decision-sync/` | 회의록 → 로그 동기화 스킬. 추출·분류·채번·파급 정리·요약까지 |

## 운영 모델 (3줄)

1. 회의록·일정 문서가 생기면 `docs/meetings/`에 날짜 접두사로 저장한다 — 원본은 다시 안 고친다.
2. "결정 반영"이라고 말한다 → `decision-sync`가 결정됨/신규 미결/보류를 분류해 `DECISIONS.md` 갱신 + POL/REQ 파급 목록 제시.
3. 대시보드·주간 보고 등 소비자는 `DECISIONS.md` **한 파일만** 읽는다 — 낡을 수 있는 곳이 한 곳뿐.

## 다른 산출물과의 관계

- `ROADMAP.md` §6(decision parking lot) → 본 로그의 **미러(요약)** 로 강등. 값이 다르면 DECISIONS.md가 정답.
- `spec-verify` 팩의 REVIEW.md → 검토 중 발견된 🔴 결정 필요 항목도 DECISIONS.md에 행으로 등재(REVIEW는 발견 기록, DECISIONS는 상태).
- POL/REQ의 `(협의 필요)` → 각 표기가 DECISIONS 행과 1:1 대응되는 게 이상적. 결정 시 함께 제거.
