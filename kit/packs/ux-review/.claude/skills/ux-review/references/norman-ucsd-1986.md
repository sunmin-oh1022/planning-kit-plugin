# User Centered System Design (Norman & Draper, 1986) 핵심 이론

"사용자 중심 디자인" 개념의 원전. 아래 개념들은 기획 판단의 근거로 인용할 때 정확히 사용하라.

## 1. 행동의 7단계 모델 (Seven Stages of Action)

사용자-시스템 상호작용의 인지 사이클. 출처: Norman의 "Cognitive Engineering" 챕터.

**실행 측 (1→4)**
1. **목표 형성 (Goal)** — 이루고 싶은 상태
2. **의도 형성 (Intention)** — 목표를 위한 구체적 의도
3. **행위 명세 (Action specification)** — 행동 순서 계획
4. **실행 (Execution)** — 인터페이스에서 물리적 실행

**평가 측 (5→7)**
5. **지각 (Perception)** — 시스템 상태 지각
6. **해석 (Interpretation)** — 지각한 것의 의미 해석
7. **평가 (Evaluation)** — 목표 대비 결과 평가

적용법: 핵심 플로우의 각 화면을 이 7단계로 워크스루한다. 어느 단계에서든 사용자가 멈칫하면 그 단계가 결함 위치다. 단계별 진단 언어를 쓰면 문제가 정확해진다 — "UI가 불편하다"(모호) 대신 "행위 명세 단계 결함: 다음 행동 선택지가 시스템 용어로 쓰여 있어 의도를 행동으로 번역하지 못함"(정확).

## 2. 두 개의 간극 (Gulf of Execution / Gulf of Evaluation)

- **실행의 간극**: 사용자의 의도 ↔ 시스템이 허용하는 행동 사이의 거리. 징후: "이걸 어떻게 하지?", 기능은 있는데 찾지 못함, 사용자 언어와 메뉴 언어의 불일치.
- **평가의 간극**: 시스템의 상태 표현 ↔ 사용자의 기대 사이의 거리. 징후: "된 건가?", 같은 행동 반복(더블 제출), 결과 확인을 위해 다른 화면으로 이동.

핵심 원칙: **간극은 시스템이 메운다.** 사용자에게 학습·추측·매뉴얼을 요구해 간극을 건너게 하는 설계는 결함이다.
- 실행의 간극 해소 수단: 가시성, 사용자 언어 레이블, 자연스러운 매핑, 다음 행동 유도
- 평가의 간극 해소 수단: 즉각적 피드백, 해석 가능한 상태 표시, 진행률, 결과의 명시적 확인

## 3. 세 가지 모델 (Design Model / User's Model / System Image)

- **디자인 모델**: 기획자가 의도한 시스템의 개념 모델
- **사용자 모델**: 사용자가 사용 경험으로 스스로 구축하는 멘탈 모델
- **시스템 이미지**: 사용자에게 보이는 모든 것 — 화면, 문구, 동작, 마케팅, 문서

**기획자는 사용자와 직접 대화할 수 없다. 오직 시스템 이미지로만 소통한다.** 사용자 모델은 시스템 이미지에서만 형성되므로, 시스템 이미지가 디자인 모델을 일관되게 드러내지 못하면 사용자는 반드시 잘못된 모델을 만든다.

적용법:
- 기획 초기: 디자인 모델을 한 문장으로 문서화하라. ("이 서비스는 ___처럼 작동한다")
- 리뷰 시: 화면·문구·동작이 서로 다른 모델을 암시하는 **모델 불일치**를 찾아라. (예: 어떤 화면은 "폴더" 은유, 다른 화면은 "태그" 은유)

## 4. 직접 조작 (Direct Manipulation) — Hutchins, Hollan & Norman

직접성(directness) = **거리(distance)** + **관여(engagement)**

- **의미적 거리**: 사용자가 생각하는 목표의 언어 ↔ 인터페이스 표현의 언어 사이 거리. 사용자가 "내 생각을 시스템 말로 번역"해야 하면 의미적 거리가 크다.
- **조음적 거리**: 표현의 형태 ↔ 의미 사이 거리. 아이콘이 기능을 닮았는가, 조작 방향이 결과 방향과 일치하는가.
- **직접 관여**: 명령을 "기술"하는 느낌이 아니라 대상을 "직접 다루는" 느낌. 드래그로 옮기기 vs 이동 명령 입력.

트레이드오프 (반드시 함께 언급): 직접 조작은 학습 용이·몰입에 유리하지만, 반복 작업·대량 처리·추상 조작에는 명령형/자동화가 유리하다. 초보자용 직접 조작과 숙련자용 단축 경로를 함께 제공하는 것이 정석.

## 5. 사용자의 소박한 이론 (Naive Theories)

사용자는 시스템을 불완전하지만 **자기 나름 일관된 이론**으로 이해하고, 그 이론으로 예측·행동한다 (diSessa, Owen, Riley).

- 오개념은 교육으로 교정하려 하지 말 것. 대신 (a) 사용자가 자연히 형성할 모델에 시스템을 맞추거나, (b) 시스템 이미지로 올바른 모델 형성을 유도하라.
- 사용자의 반복 오류는 그들의 이론이 시스템과 어긋난다는 신호다. 오류 로그·CS 문의는 사용자 모델을 역추적하는 최고의 데이터다.

## 6. 활동의 구조와 중단 (Cypher; Miyata & Norman)

실제 사용자 활동은 단일 과제의 깔끔한 수행이 아니다. 여러 활동이 뒤섞이고, 중단(interruption)과 재개(resumption)가 기본값이다.

기획 요구사항으로의 번역:
- 모든 플로우는 중간 이탈을 전제로 설계 (자동 임시저장, 작성 중 이탈 경고)
- 복귀 시 맥락 복원 — "어디까지 했는지"를 시스템이 답해야 한다
- 긴 과제는 중단 가능한 단위로 분할하고 각 단위 완료를 명시

## 7. 도움과 정보 흐름 (Bannon, O'Malley, Owen)

- **사용자는 매뉴얼보다 사람에게 묻는다** ("Helping Users Help Each Other"). 도움 설계에 사회적 경로(공유, 커뮤니티, 리뷰)를 포함하라.
- **"Answers First, Then Questions"**: 사용자가 질문을 형성하기 전에 답을 먼저 노출하라. 엠프티 스테이트 가이드, 상황별 힌트, 예시 데이터가 이 원칙의 구현이다.
- 도움말은 사용자가 "무엇을 모르는지도 모르는" 상태를 전제로 설계한다. 검색형 도움말만으로는 부족한 이유.

## 8. 배경 사상

- **인터페이스가 곧 시스템**: 사용자 관점에서 시스템은 인터페이스로만 존재한다.
- **과제 중심**: 사용자는 시스템을 쓰고 싶은 게 아니라 일을 끝내고 싶다. 좋은 도구는 투명해져서 사용자가 과제에 몰입하게 한다.
- **근사 이론의 실용주의**: 완벽한 인지 이론을 기다리지 말고, 방향이 옳은 근사 법칙(단기기억 한계, 주의 자원 한계)으로 빠르게 판단하라.
- **트레이드오프 명시**: 모든 디자인 결정은 무언가를 포기한다. 무엇을 얻고 잃는지 기록하는 것이 사용자 중심 설계의 정직함이다.
