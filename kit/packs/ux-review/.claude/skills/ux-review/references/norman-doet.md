# The Design of Everyday Things (Norman, 1988 / 개정판 2013) 핵심 이론

UCSD(1986)의 학술 개념을 대중화하고 확장한 저작. 아래 용어는 개정판(2013) 기준으로 정확히 구분해 사용하라.

## 1. 발견 가능성의 6원칙

사용자가 "무엇을 할 수 있고, 지금 무슨 일이 일어났는지" 알 수 있게 하는 장치들.

### 어포던스 (Affordance)
객체와 행위자 사이의 **관계** — 그 객체로 무엇을 할 수 있는가. 버튼은 누름을, 입력창은 입력을 어포드한다.
주의: 어포던스는 "존재하는 가능성"이고, 그것이 보이는가는 별개 문제다. 흔한 오용("어포던스가 없다" = 사실 "시그니파이어가 없다")을 피하라.

### 시그니파이어 (Signifier)
어포던스의 존재를 **알리는 신호** — 어디를 누를 수 있는지, 밀지 당길지를 알려주는 표시. 밑줄 링크, 버튼의 입체감, 스크롤 힌트로 잘린 콘텐츠.
리뷰 시 질문: "할 수 있는 행동(어포던스)은 있는데 그걸 알리는 신호(시그니파이어)가 있는가?" 플랫 디자인에서 가장 자주 깨지는 원칙.

### 제약 (Constraints)
가능한 행동을 줄여 올바른 행동으로 유도하는 장치. 물리적(USB 방향), 문화적(빨강=정지), 의미적(맥락상 말이 되는 것), 논리적(남은 것이 하나뿐) 제약. 잘못된 입력을 에러로 처리하기보다 **애초에 불가능하게** 만드는 것이 상위 설계다 (비활성 버튼, 날짜 피커, 입력 마스크).

### 매핑 (Mapping)
조작과 결과 사이의 공간적·논리적 대응. 좋은 매핑은 설명이 필요 없다 (오른쪽 스와이프 → 오른쪽으로 이동). 리뷰 시: 조작의 배치·방향이 결과의 배치·방향과 일치하는가?

### 피드백 (Feedback)
행동의 결과를 즉각적이고 해석 가능하게 알리는 것. 원칙: 즉각적일 것(0.1초 내 반응 시작), 정보를 담을 것("에러 발생" 금지 — 무엇이, 왜, 어떻게 하면 되는지), 과하지 않을 것(피드백 폭탄은 무피드백만큼 나쁘다).

### 개념 모델 (Conceptual Model)
시스템이 어떻게 작동하는지에 대한 단순화된 설명. 좋은 개념 모델은 사용자가 결과를 **예측**하게 한다. 예측이 가능하면 학습·복구·응용이 전부 쉬워진다.

## 2. 세상 속 지식 vs 머릿속 지식

행동에 필요한 지식을 사용자의 기억(머릿속)에 요구할지, 인터페이스(세상 속)에 배치할지의 선택.

- 세상 속 지식: 배울 필요 없음, 그러나 매번 지각·해석 비용 발생 (메뉴, 레이블, 마법사형 UI)
- 머릿속 지식: 학습 비용이 들지만 숙련 후 빠름 (단축키, 제스처, 명령어)

원칙: **회상(recall)보다 재인(recognition)**. 사용자가 기억해내게 하지 말고 보고 고르게 하라. 단, 숙련자를 위한 머릿속 지식 경로(단축키 등)를 병행 제공하라.

## 3. 오류 설계 (Human Error? No, Bad Design)

### 실수(Slip) vs 착오(Mistake)
- **실수(slip)**: 목표는 옳았으나 실행이 어긋남. 숙련자에게 잦다. (옆 버튼 오터치, 자동조종 상태로 엉뚱한 항목 선택)
- **착오(mistake)**: 목표·계획 자체가 틀림. 잘못된 멘탈 모델에서 비롯된다. (기능의 용도를 오해)

구분이 중요한 이유: 처방이 다르다. 실수 → 타깃 크기, 간격, 확인 단계, 실행취소. 착오 → 개념 모델 전달 개선, 시스템 이미지 수정.

### 오류 대응 설계 순서
1. **원천 차단**: 제약으로 오류를 불가능하게
2. **감지와 복구**: 실행취소(undo)를 기본 제공 — 확인 대화상자보다 실행취소가 우월하다 (확인창은 습관적으로 눌러 무력화됨)
3. **관용**: 파괴적 행동(삭제, 전송, 결제)일수록 되돌릴 수단을 제공
4. **비난 금지**: 오류 메시지는 사용자를 탓하지 않고 복구 경로를 안내

## 4. 행동 7단계와 디자인 질문 (DOET 버전)

UCSD의 7단계를 디자인 체크 질문으로 변환한 것:
1. 무엇을 이루고 싶은가? (목표)
2. 대안이 되는 행동들은 무엇인가? (계획)
3. 지금 무슨 행동을 할 수 있는가? (명세)
4. 그것을 어떻게 하는가? (실행)
5. 무슨 일이 일어났는가? (지각)
6. 그것은 무슨 뜻인가? (해석)
7. 원하는 대로 되었는가? (비교)

각 질문에 인터페이스가 답하지 못하면 그 지점이 결함이다. 1-4 실패 = 실행의 간극, 5-7 실패 = 평가의 간극.

## 5. 인간 중심 디자인 프로세스

관찰 → 아이디어 생성 → 프로토타이핑 → 테스트의 반복 사이클. 핵심 태도:
- **올바른 문제를 풀어라**: 요청받은 문제는 대개 증상이다. 근본 문제를 다시 정의하라 (노먼의 "이중 다이아몬드").
- 사용자를 관찰하라 — 말하는 것이 아니라 **하는 것**을. 사람들은 자기 행동을 정확히 보고하지 못한다.
- 활동 중심 디자인: 개별 과제가 아니라 활동 전체(준비-수행-정리)를 지원하라.
