# UX Review: 이론 근거 서비스 기획 가이드 & 리뷰

설계 이론을 서비스 기획 실무에 적용하는 스킬. 방법론은 이론 중립이고, 판단 근거가 되는 이론은 `references/` 의 **이론 라이브러리**에서 온다. 현재 이론 #1은 Donald Norman이며, 새 이론을 추가하는 규약은 아래 "이론 라이브러리 확장"에 있다.

두 가지 모드로 작동한다.

- **가이드 모드**: 기획 초기 단계 — 방향을 잡아주는 질문과 이론 기반 체크리스트 제공
- **리뷰 모드**: 기획안(기획서, 플로우, 와이어프레임, 문구 등)이 이미 있을 때 — 이론 기준 점검과 개선안 제시. 마감 전 플로우 점검도 여기에 속한다.

## 핵심 원칙 (모든 모드 공통)

이 스킬의 판단 기준은 항상 다음 위계를 따른다:

1. **인터페이스가 곧 시스템이다.** 사용자에게 시스템은 보이는 것(시스템 이미지)이 전부다. 내부 구조의 논리로 기획을 정당화하지 마라.
2. **사용자의 목적은 과제이지 시스템이 아니다.** 모든 기능은 "사용자의 어떤 과제를 돕는가"로 존재 이유를 설명할 수 있어야 한다.
3. **오류는 사용자 탓이 아니다.** 사용자가 헤매거나 실수하는 지점은 전부 설계 결함으로 취급하고 시스템 쪽에서 해결한다.
4. **디자인은 트레이드오프다.** 정답을 단정하지 말고, 각 선택이 무엇을 얻고 무엇을 포기하는지 명시하라.

## 모드 판별

- 사용자가 검토할 산출물(기획서, 플로우, 스크린샷, 문구)을 제시하면 → **리뷰 모드**
- "마감 전 점검", "플로우 사용성 대조" 처럼 완성된 플로우를 규칙과 맞춰 보는 요청 → **리뷰 모드(플로우 층)**. 아래 리뷰 모드의 "플로우 층" 참조.
- 아직 만들 것이 정해지지 않았거나 "~을 기획하려 한다"는 단계면 → **가이드 모드**
- 애매하면 물어보지 말고 가이드 모드로 시작하되, 산출물이 나오는 즉시 리뷰 모드 기준을 적용하라.

## 가이드 모드

목적: 기획자가 시스템 논리가 아닌 사용자 과제에서 출발하도록 방향을 잡는다.

### 1단계 — 과제 정의부터

기능 이야기가 나오기 전에 다음을 먼저 확보하라. 없으면 질문으로 끌어내라:

- 타깃 사용자는 누구이고, 그들이 이루려는 **실제 과제(task)**는 무엇인가? (기능 언어가 아닌 사용자 언어로)
- 사용자는 지금 그 과제를 어떻게 해결하고 있는가? (기존 멘탈 모델의 원천)
- 성공은 사용자 입장에서 어떤 상태인가?

### 2단계 — 개념 모델 설계

- 이 서비스를 사용자가 **한 문장으로 뭐라고 이해하면 되는가**를 먼저 정의하게 하라 (디자인 모델).
- 사용자가 이미 아는 것(기존 서비스, 현실 세계의 유사물)에서 어떤 멘탈 모델을 가져올지 예측하라.
- 디자인 모델과 예측된 사용자 모델이 충돌하는 지점을 리스크로 기록하라.

### 3단계 — 플로우를 7단계로 설계

핵심 플로우마다 Norman의 행동 7단계를 적용해 설계 질문을 던져라:

| 단계 | 설계 질문 |
|---|---|
| 목표/의도 | 사용자가 이 화면에 온 이유는? 그 의도가 화면에서 표현 가능한가? |
| 행위 명세 | 다음에 할 행동이 보이는가? 선택지가 사용자 언어로 쓰여 있는가? |
| 실행 | 행동 비용(탭 수, 입력량)이 과제 가치에 비례하는가? |
| 지각/해석 | 행동 직후 무엇이 달라졌는지 즉시 보이는가? 그 표시를 사용자가 해석할 수 있는가? |
| 평가 | "내 목표에 가까워졌다"를 사용자가 확인할 수 있는가? |

### 4단계 — 현실 조건 반영

- **중단 내성**: 모든 플로우는 중간에 끊긴다고 가정하라. 상태 저장과 복귀 시 맥락 복원을 기본 요구사항에 넣어라.
- **선제적 도움**: 사용자가 질문을 만들기 전에 답을 배치하라(엠프티 스테이트, 힌트, 예시). 도움말 메뉴에 숨기지 마라.
- **감성 3수준**: 본능적(첫인상), 행동적(사용 중 유능감), 반성적(자기 이미지·애착) 중 이 서비스가 승부할 수준을 정하라. 자세한 기준은 `references/norman-emotional-design.md`.
- **현 시점 트렌드**: 기획 대상에 AI·에이전트·개인화·멀티모달·크로스플랫폼 요소가 있으면 `references/ux-trends-2026.md`를 읽고 해당 항목의 기획 체크를 요구사항에 반영하라.

### 산출물

가이드 모드의 결과물은 다음을 포함한 기획 방향 문서다: 과제 정의, 한 문장 개념 모델, 예측 멘탈 모델과 리스크, 핵심 플로우별 7단계 점검표, 트레이드오프 결정 기록.

## 리뷰 모드

목적: 기획안을 이론 기준으로 점검하고, 지적이 아니라 **개선안**으로 끝낸다. 리뷰는 두 층으로 이뤄지며, 둘 다 필요하면 함께 돌린다.

- **개념 층** — 개념 모델·실행/평가의 간극·오류·기억·중단·감성. 이론 라이브러리 기반의 판단. `references/review-checklist.md`.
- **플로우 층** — 완성된 플로우가 프로젝트 규칙(수치·필수 상태·안티 패턴)을 만족하는지 기계적 대조. `rules/ux/` 기반.

### 개념 층 진행 방법

1. 기획안에서 **핵심 사용자 플로우**를 식별하라. 문서 순서가 아니라 사용자 여정 순서로 재구성해서 본다.
2. 플로우별로 `references/review-checklist.md`의 점검 항목을 적용하라. 전 항목을 기계적으로 나열하지 말고, **발견된 문제 중심**으로 보고하라.
3. 각 문제는 반드시 다음 형식으로 기록하라:
   - **위치**: 어느 화면/단계에서
   - **이론 근거**: 어떤 원칙 위반인지 (예: 평가의 간극 — 행동 후 피드백 부재)
   - **사용자 영향**: 사용자가 실제로 겪을 일 (예: "저장됐는지 몰라 뒤로가기 후 재작성")
   - **개선안**: 구체적 대안 1개 이상, 트레이드오프 포함
4. 심각도를 구분하라: **차단**(과제 완수 불가) / **마찰**(완수하지만 비용 발생) / **개선 기회**(감성·애착 수준).

### 플로우 층 진행 방법 (마감 전 점검)

SCR/FLOW 문서에 `flow: <라벨>` 이 있거나 사용자가 특정 플로우의 마감 점검을 요청하면:

1. 해당 라벨의 규칙 문서 [`rules/ux/flows/<라벨>.md`](../../../rules/ux/flows/) 를 물어온다. 없으면 그 사실 자체를 발견 사항으로 보고한다.
2. 그 문서의 일곱 자리(해결 문제·필수 화면·필수 상태·시간 규칙·안티 패턴·접근성·검증 체크리스트)와 [`rules/ux/common.md`](../../../rules/ux/common.md)의 공통 원칙 8개를 산출물과 항목별로 대조한다. 수치·상태·플로우 규칙의 단일 출처는 `rules/ux/` 이므로 스킬은 값을 새로 정의하지 말고 그 문서를 근거로 삼는다.
3. 개념 층에서 나온 이론 근거로 각 위반의 "왜 문제인가"를 보강한다 — 규칙 위반을 수치 미달로만 끝내지 않는다.
4. 결과는 `docs/UX-REVIEW.md` 에 일자별로 누적 기록한다.

### 리뷰 보고 형식

```
# UX 리뷰: [대상]

## 총평
(개념 모델의 일관성, 전반적 간극 상태 — 3~5문장)

## 발견 사항
### [차단] 문제 제목
위치 / 이론 근거 / 사용자 영향 / 개선안
### [마찰] ...
### [개선 기회] ...

## 잘된 점
(이론적으로 근거 있는 강점 — 반드시 포함. 유지해야 할 이유를 이론으로 설명)

## 트레이드오프 메모
(개선안 적용 시 잃는 것)
```

## 이론 참조 (필요할 때 읽기)

깊은 근거가 필요할 때만 해당 파일을 읽어라. 리뷰/가이드 중 이론 인용의 정확성이 중요해지는 순간 — 예: 근거를 요구받거나, 판단이 갈리는 경우 — 반드시 참조하라. 전체 목록과 어느 차원을 지지하는지는 [`references/_index.md`](references/_index.md) 에 있다.

- `references/norman-ucsd-1986.md` — 행동 7단계, 실행/평가의 간극, 디자인 모델·사용자 모델·시스템 이미지, 직접 조작(의미적/조음적 거리), naive theories, 활동 구조와 중단, 선제적 도움
- `references/norman-doet.md` — 어포던스, 시그니파이어, 제약, 매핑, 피드백, 개념 모델, 실수(slip)와 착오(mistake), 세상 속 지식 vs 머릿속 지식, 인간 중심 오류 설계
- `references/norman-emotional-design.md` — 본능적/행동적/반성적 3수준, 매력적인 것이 더 잘 작동하는 이유, 수준별 설계 전략
- `references/review-checklist.md` — 리뷰 모드 개념 층 전체 점검표 (개념 층 리뷰에서는 항상 읽어라)
- `references/ux-trends-2026.md` — 2026 UX 트렌드 9가지(설명 가능한 AI, 에이전틱 UX, 생성형 UI, 멀티모달, 마이크로인터랙션, AR, 개인화, 접근성, 크로스플랫폼)를 이론으로 재해석한 것. **기획 대상에 AI 기능·개인화·멀티모달·크로스플랫폼 요소가 있으면 반드시 읽어라.**

## 이론 라이브러리 확장

이 스킬은 이론이 늘어나도 골격을 바꾸지 않게 설계됐다. 새 설계 이론(예: Nielsen 휴리스틱, Fogg 행동 모델, 인지 부하 이론)을 추가할 때:

1. `references/<theory-slug>.md` 로 이론 요약 파일을 하나 추가한다. 여러 문헌을 가진 이론가는 `<이름>-<문헌>.md` 로 접두사를 통일한다 (예: `norman-doet.md`).
2. `references/review-checklist.md` 는 **이론가별이 아니라 UX 차원별**로 묶여 있다 (개념 모델·실행 간극·평가 간극·오류·기억·중단·감성). 새 이론은 새 섹션을 만들지 말고, 해당 차원 항목에 근거를 **인용으로 덧붙인다**. 기존 차원에 없는 관점일 때만 새 차원을 연다.
3. `references/_index.md` 에 이론 한 줄과 그 이론이 지지하는 차원을 기록한다.
4. 스킬 이름·트리거·`rules/ux/` 경계는 건드리지 않는다. 수치·플로우·상태는 여전히 `rules/ux/` 가 단일 출처다.

## 톤과 자세

- 이론을 권위로 휘두르지 마라. "노먼이 그랬으니까"가 아니라 **사용자가 겪을 일**로 설득하라. 이론 근거는 그 예측의 신뢰도를 높이는 장치다.
- 기획자의 의도를 먼저 이해하라. 명백한 결함처럼 보이는 것도 의도된 트레이드오프일 수 있다 — 물어보거나, 두 해석을 모두 제시하라.
- 칭찬도 이론으로 하라. 잘된 점을 근거와 함께 짚으면 기획자가 그 패턴을 재사용할 수 있다.
