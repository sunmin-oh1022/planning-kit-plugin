# REVIEW.md — 기획 문서 검증 기록

검증은 두 가지 방식으로 한다. 가볍게 한 번 훑을 땐 spec-self-review 를 쓰고, 도메인이나 버전 단위로 여러 에이전트가 교차검증할 땐 spec-verify-loop 를 쓴다. 둘 다 같은 7축으로 보고 같은 등급(🔴 결정 필요, 🟡 보강, 🟢 경미, 처리되면 🟩)을 쓴다. 결과는 이 파일에 날짜별로 쌓는다. 방법론의 단일 진실은 rules/methodology/README.md 의 Phase 2 다.

## 2026-06-24 · 도메인 USER

spec-verify-loop 를 normal 깊이로 한 번 돌렸다. 에이전트 11개가 붙어서 확정 1건, 환각으로 걸러낸 건 0건이 나왔고, 종합 판정은 "보강 1건"이다.

기계검증(check-docs.sh)은 통과했다. 실패는 없고 경고만 네 개 남았는데, CLAUDE.md 심링크가 아직 없는 것, TODO 자리표시자 83줄, REQ-101부터 103까지 TC 연결이 빈 것, 1초 검증 명령이 아직 정해지지 않은 것이다. 넷 다 Phase 0/1 이 진행 중일 때 으레 나오는 신호라 지금은 문제가 아니다.

확정된 한 건은 단일 진실 위반이다(🟡 보강). docs/POL.md 8번째 줄에서 닉네임 길이를 "2–12자"라고 직접 적어두었는데, 이 값의 단일 진실은 glossary.md 다. 같은 값이 두 곳에 있으면 나중에 한쪽만 고쳐져 서로 어긋날 위험이 생긴다. 회의자 세 명이 모두 실재하는 문제로 판정했다. 고치는 방향은 POL-001 에서 자릿수를 직접 쓰지 말고 glossary 의 닉네임 정의를 가리키게 하는 것이다. 가령 "닉네임 형식 위반 차단(길이·문자 제약은 glossary.md 닉네임 정의를 따름), 특수문자 불가"처럼 적으면, 범위 값은 glossary 한 곳에만 남는다.

아직 적용하지 않았다. 고칠지 말지는 기획자가 정한다.
