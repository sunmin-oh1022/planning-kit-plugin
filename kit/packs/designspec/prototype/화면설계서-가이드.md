# 화면설계서 · 프로토타입 제작 가이드 (재사용 템플릿 킷)

> **목적**: 이 가이드는 특정 프로젝트에 종속되지 않는 **화면설계서/프로토타입 제작 컨벤션**만 모은 추출용 문서입니다.
> 새 프로젝트에서 동일한 산출물을 만들 때 이 문서 + `_template.designspec.html` + `build-pdf.sh` 를 복사해 시작하세요.
> 이 프로젝트({{PROJECT_NAME}})의 실제 적용 사례는 `prototype/README.md`, `[USER]/[ADMIN] 화면설계서.designspec.html` 참조.

본 가이드는 **재사용 가능한 패턴**만 담습니다. 프로젝트마다 달라지는 것(용어·정책 내용·화면·역할)은 각 프로젝트의 `docs/`에서 정의합니다. → [§8 새 프로젝트 적용 체크리스트](#8-새-프로젝트-적용-체크리스트)

## 1. 산출물 — 화면당 2종
| 산출물 | 형식 | 용도 |
|---|---|---|
| **동작 HTML 프로토타입** | 정적 HTML + 약간의 JS, 빌드 없음, 흑백 와이어프레임 | 리뷰·의사결정. 상태 토글(정상/로딩/빈/에러/권한없음/오프라인)·권한 토글로 시연 |
| **화면설계서 PDF** | A4 가로, 피그마 스타일(목업 70% + Description 30%) | 고객사 전달. `*.designspec.html` → `build-pdf.sh` 로 렌더 |

- **도메인 단위로 묶는다**: 프로토타입 = 단일 SPA(`[{DOMAIN}] 프로토타입_v{버전}.html`, 메뉴 클릭=화면 전환·해시 라우팅), 화면설계서 = 멀티페이지(`[{DOMAIN}] 화면설계서.designspec.html` → `_v{버전}.pdf`).
- 흑백 기조, 색은 **포인트 컬러 뱃지**(`--pt`)와 **상태칩**(`--chip`)만.

## 2. 문서 구조 (페이지 순서)
```
표지(cover) · 프로젝트 개요(summary) · 개정이력(revision) · 정보구조(IA)
  · 공통 정의(권한·표시·메시지)            ← 문서당 1개
  · [화면별 2페이지] × N                    ← 화면 1개 = .page 2개
```

### 2-1. 화면별 page1 — 목업 70% + Description 30%
- 좌 **목업**(흑백). 영역마다 **포인트 컬러 번호 뱃지 ❶~**, 뱃지는 **좌측 거터**(`.main{padding-left:28px}`, `.reg>.bdg{left:-24px}`)에 둬 콘텐츠와 겹치지 않게.
- 우 **Description**: `뱃지 + 영역/컴포넌트명`(헤딩) → 글머리 **동작·인터랙션** → 글머리 **데이터/표시 규칙**(세부는 `ㄴ`). 협의 항목은 `<span class="opn">협의</span>`.
- 상단바: `Screen Path / Status`(브레드크럼) · 상태칩(버전) · `Screen ID`.

### 2-2. 화면별 page2 — ★ 표준 구성 (순서 고정)
| # | 섹션 | 역할 |
|---|---|---|
| 1 | **화면 기본 정보** | 화면 ID/명 · 관련 요구 · 화면 목적 · 관련 정책 |
| 2 | **컴포넌트 액션 정의** | "누르면 어떻게 되나" — `컴포넌트(❶~ 번호) · 트리거 · 동작·결과 · 검증·예외 · 관련 POL`. 목업 뱃지와 1:1 |
| 3 | **유효성·메시지 정의** | "케이스별 검사 + 결과 카피" — `케이스 · 조건/결과 · 메시지 문구(실제) · 표시 방식(토스트/다이얼로그/인라인/배너) · 관련 POL` |
| 4 | **상태 매트릭스(6)** | 정상/로딩/빈/에러/권한없음/오프라인 × 표시 내용 · 행동 유도 |
| 5 | **화면 내 기능 플로우** | SVG 다이어그램. 폰트 10px(표 본문과 동일), viewBox 폭으로 1:1 렌더 |

> **역할 분리 원칙**: Description = "무엇을 보여주나" / 액션 정의 = "누르면 어떻게 되나" / 유효성·메시지 = "무엇을 검사하고 어떤 문구를 주나". 셋이 겹치지 않게.

### 2-3. 공통 정의 페이지 (IA 다음, 문서당 1개)
문서 전체에 적용되는 cross-cutting 기준 3종:
1. **권한 매트릭스** — 역할 × 기능·데이터(노출/실행). 단일 역할 콘솔이면 "기능 × 접근 권한 + 비고".
2. **데이터 표시 규칙** — 숫자·단위·빈값(미제공)·상태 라벨·날짜/일시·집계 시각·페이징 등 표기 포맷.
3. **메시지 톤·유형 공통 범례** — 성공/실패·에러/확인/경고/안내 × 표시 방식 × 문구 패턴. (→ 화면별 유효성·메시지 표는 이 범례를 따름. 이 표는 **그대로 재사용 가능**)

## 3. 레이아웃 규칙 (CSS 고정값)
- **가로 폭 고정 297mm, 세로 자동 확장**: `.page{ width:297mm; min-height:210mm; padding:8mm 11mm }`. 세로는 **최소 210mm ~ 무제한**. ⛔ A4 세로에 욱여넣으려 폰트·여백을 반복 조정하지 않는다(토큰 낭비).
- **목업 창 고정 높이**: `.win{ height:138mm; display:flex; flex-direction:column }` — 정보가 적어도 납작해지지 않고 실제 화면처럼.
- **뱃지 잘림 방지**: 클리핑 컨테이너에 `overflow:hidden` 금지. 뱃지는 거터 + `box-shadow:0 0 0 2px #fff` 링.
- **플로우 폭**: `svg{ width:<viewBox px>; max-width:100% }` — 내용만큼만, 과대 폭 방지. `width:100%`(텍스트까지 확대됨) 금지.
- 인쇄 배경 출력: `print-color-adjust:exact`.

## 4. PDF 빌드 (`build-pdf.sh`)
- 각 `.page` 의 실제 높이를 측정 → **정적 `@page{ size:297mm Hmm }` 을 페이지별로 주입**해 한 장씩 렌더 → PDFKit로 합침.
- ⚠️ **동적 JS `@page` 주입은 Chrome이 무시**한다. 반드시 정적 주입(sed, 구분자 `|`).
- 빌드 버퍼 0.4mm(`round(h/96*25.4 + 0.4, 1)`).
- 사용: `bash build-pdf.sh "<src>.designspec.html" "<out>_v0.1.pdf"` · 일괄: `build-all.sh`(`_template` 제외, 한글 파일명 NFC/NFD 회피).

## 5. 파일명·버전 체계
- 소스 `[{DOMAIN}] 화면설계서.designspec.html` → 전달본 `[{DOMAIN}] 화면설계서_v{X.Y}.pdf`.
- 프로토타입 `[{DOMAIN}] 프로토타입_v{X.Y}.html`(단일 SPA). 각 화면 Page Info에 매칭 프로토타입 `파일#해시` 표기.
- **버전 매칭**: 프로토타입 `vX.Y` = 화면설계서 `vX.Y`. 버전 업은 **명시 요청 시에만** 새 파일 생성(기존 보존).

## 6. ★ 작업 방식 (워크플로우) — 꼭 지킬 것
> 이 절은 "문서/코드에 안 적혀 있지만 반드시 지켜야 하는 진행 방식"입니다.

- **HTML 수정·확인 ↔ PDF 생성은 별개 단계.** `.designspec.html`/프로토타입을 고치고 브라우저로 확인하는 작업과, 전달용 PDF 빌드를 분리한다. **PDF는 요청이 있을 때만 빌드**(HTML 수정 언급만으로 자동 빌드 금지).
- **프로토타입 ↔ 설계서는 자동 동기화되지 않는다.** 두 파일은 별개이며, 한쪽을 고치면 **수동으로(diff 기반) 반영**해야 한다. 한 번에 한쪽만 수정 권장.
  - 정방향(설계서→프로토타입)·역방향(프로토타입→설계서) 모두 가능. 어느 쪽을 원본으로 둘지는 그때그때 선택.
  - **목업 문구 ↔ 목업** 1:1 반영. **Description·화면 목적·동작/상태 토글**은 목업에 대응 영역이 없어, 해석해서 알맞은 섹션(Description 등)에 옮긴다.
- **수정분 탐지 = VS Code 로컬 히스토리 diff**가 가장 정확. `~/Library/Application Support/Code/User/History/<hash>/entries.json` 이 파일 URI를 참조, 스냅샷을 timestamp 순 정렬 → 수정 전(직전 스냅샷) vs 현재 파일 diff로 바뀐 부분만 추출.
- ⛔ **개정이력(revision) 페이지는 작성자(기획자)가 직접 관리.** 자동으로 행 추가·수정·현행화하지 않는다(HTML 주석에도 명시).
- 설계 **범위**는 프로젝트별로 먼저 합의한다(예: 어떤 콘솔/도메인을 직접 설계할지, 무엇을 제외할지).

## 7. 정책 패턴 (POL — 프로젝트마다 번호는 다를 수 있음)
재사용을 권장하는 표준 정책 패턴:
- **날짜·시간 표기**(예: POL-016): 일시 `YYYY.MM.DD(요일) 오전/오후 h:mm` · 일자 `YYYY.MM.DD` · 간략 `M월 D일`(0 제외) · 시간 `오전/오후 h:mm`. 12시간제, 시·분까지. **문서 메타(작성/개정일자)는 예외 — `YYYY-MM-DD`.** 단일 진실 = `glossary.md`.
- **화면 크기**(예: POL-017): PC 디자인 1440·**최소 1280** / 모바일 디자인 375·**최소 360**(320 미지원). 폭이 기준(높이는 세로 스크롤 허용). 데이터 콘솔=데스크톱 우선(미만 시 안내 배너), 홍보성 화면=완전 반응형.
- **페이징·노출 건수**: 10/20/50/100, 1페이지 우선 표출.
- **입력 검증**: 오류별 구체·명확 메시지(막연한 '오류' 금지).

## 8. 새 프로젝트 적용 체크리스트
1. `_template.designspec.html` · `build-pdf.sh` · `build-all.sh` · 본 가이드 복사.
2. **표지/개요(summary)** — 로고·프로젝트명·목표·기간·연계·자료연결을 새 프로젝트로 교체.
3. **IA 페이지** — 해당 도메인의 정보구조 표 삽입(주석 해제 후 채움).
4. **공통 정의 페이지** — 권한 매트릭스·데이터 표시 규칙을 새 프로젝트 역할/포맷으로 채움(메시지 톤 범례는 그대로 재사용).
5. **화면 페이지** — 템플릿의 [PAGE 1]/[PAGE 2] 주석 블록을 화면 수만큼 복제·채움. page2 표준 5섹션 순서 유지.
6. **개정이력** — v0.1 1행만 두고 이후는 작성자가 직접 관리.
7. 프로젝트 고유 정의(`docs/glossary.md`·`POL.md`·요구사항·역할)는 별도 작성. 날짜·시간/화면 크기 정책 번호만 맞춰 연결.
8. 프로토타입은 `_template` 의 상태/권한 토글 구조를 따와 도메인 화면 구성.
