# servicekit 사용설명서

servicekit은 기획자가 요구사항을 정리해서 화면설계서까지 만들어내는 한 번의 프로세스를, 같은 저장소 안에서 반복해 돌리도록 짠 도구이다.<br>
StarterKit이 기획 초안을 잡는 데까지였다면, 릴리즈킷은 그 위에서 프로토타입으로 움직임을 확인하고, 문서를 단일 진실로 정리하고, 화면설계서를 뽑아 배포하고, 다음 버전을 여는 데까지 이어진다.

이 문서는 그 프로세스를 처음 경험하는 사람을 위한 안내서다. <br>
무엇을 어디서부터 하는지, 어디까지 사람이 하고 어디부터 AI에게 맡기는지를 순서대로 따라가며 설명한다. <br>
명령어와 규칙을 항목별로 찾아보려면 SETUP.md 와 rules/methodology/README.md 가 더 빠르다. 

## 프로세스는 어떻게 구성되어 있는가

일은 늘 같은 길을 따라간다. <br>
무엇을 만들지 정하는 데서 시작해서, 그걸 docs 에 사실로 적고, 프로토타입으로 움직임을 확인하고, 검증으로 빠진 곳을 메운 다음, 화면설계서로 시각화해 배포한다. <br>
배포하고 나면 다음 버전 라인을 열고, 무엇을 왜 했는지 기록으로 남긴다.

이 길에는 지켜야 할 약속이 하나 있다. <br>
프로토타입에서 화면설계서로 바로 건너뛰지 않는다. <br>
새 요건이나 용어, 정책은 반드시 docs 를 거친다. docs 가 모든 사실의 단일 진실이고, 화면설계서는 거기서 뽑아낸 결과물이기 때문이다. <br>
이 순서를 건너뛰면 같은 내용이 프로토타입과 설계서에서 서로 다르게 적히고, 나중에 어느 쪽이 맞는지 알 수 없게 된다.

## 프로젝트 진행을 위한 딱 한 번의 준비

프로젝트를 처음 세울 때만 하는 셋업이다. <br>
이 폴더를 통째로 복사해 프로젝트 이름으로 바꾸고, git 을 초기화하고, 곳곳에 박혀 있는 `(TODO …)` 자리를 채운다.

이 과정은 AI 에게 맡겨도 된다. <br>
"Phase 0 환경 셋업 해줘. git 초기화하고 CLAUDE.md 의 TODO 채워줘" 정도로 시작하면 된다. <br>
어디까지 진행되었는지는 언제든 한 줄로 확인할 수 있다.

```bash
bash scripts/check-docs.sh
```

빨간 표시(✗)가 없고 노란 경고(!)만 남았다면 준비가 거의 끝난 것이다. <br>
경고는 대부분 아직 채우는 중이라 나오는 신호라서, 셋업이 진행될수록 하나씩 사라진다. 자세한 절차와 placeholder 종류는 SETUP.md 에 정리되어 있다.

## 처음으로 시작하는 법

여기서부터가 실제 프로세스다. 이해를 돕기 위해 "사용자 콘솔에 닉네임 변경 기능을 넣는다"는 예시로 따라가 보자.

**무엇을 만들지 한 줄로 적는다.** 
닉네임을 바꿀 수 있어야 하고, 길이와 문자에 제한이 있고, 잘못 입력하면 막아야 한다. <br>
이 단계는 온전히 기획자의 몫이다. 무엇을 왜 만드는지는 사람이 판단할 영역이지 AI 가 채워줄 자리가 아니다.

**그 요구를 docs 에 사실로 박는다.** 
요건은 REQ, 정책은 POL, 용어 정의는 glossary, 화면과 상태는 SCR, 검증 기준은 TC 에 적는다. 닉네임의 길이 같은 값은 한 곳에만 둔다. <br>
glossary 에 "닉네임은 2~12자"라고 적었으면 POL 에서는 그 값을 다시 쓰지 않고 glossary 를 가리킨다. <br>
같은 값이 두 군데 있으면 언젠가 한쪽만 바뀌어 어긋나기 때문이다. 이 작업은 함께 한다. <br>
정의와 정책과 콘텐츠는 사람이 정하고, 문서 형식에 맞춰 정리하고 초안을 잡는 일은 AI 에게 맡긴다.

**docs 가 서면 프로토타입으로 움직임을 본다.** 
정적인 HTML 로 화면이 실제로 어떻게 동작하는지 눈으로 확인하는 단계다. <br>
만들어 달라고 AI 에게 맡기고, 나온 결과를 사람이 검토한다. 보다가 빠진 흐름이나 어색한 상태가 보이면 프로토타입만 고치지 말고 docs 로 돌아가 고친다. <br>
단일 진실은 늘 docs 다.

**한 번의 프로세스를 돌았으면 검증으로 구멍을 찾는다.** 
마감 전에 문서에 구멍이나 모순이 없는지 확인한다. <br>
가볍게 훑을 땐 "셀프 검토 해줘"라고 하면 spec-self-review 가 돌고, 도메인이나 버전 단위로 꼼꼼히 볼 땐 "USER 도메인 검증 루프 돌려줘"라고 하면 spec-verify-loop 가 여러 에이전트로 교차검증한다. <br>
AI가 잡을 수 있는 정합성은 `bash scripts/check-docs.sh` 가 1초 만에 확인한다. <br>
검증이 올린 지적 가운데 빨간 항목(결정이 필요한 것)은 AI 가 고치지 않고 남겨둔다. <br>
고칠지 말지는 기획자가 정한다. 결과는 docs/REVIEW.md 에 날짜별로 쌓인다.

**구멍을 메웠으면 화면설계서를 뽑는다.** 
새 도메인이면 템플릿에서 한 줄로 만든다.

```bash
bash scripts/new-domain.sh USER 사용자콘솔
```

그러면 `prototype/user/[USER] 화면설계서.designspec.html` 이 생기고, 채워야 할 자리 목록이 함께 출력된다. <br>
그 자리를 docs 기준으로 채우고, 화면마다 두 페이지짜리 섹션을 넣는다. 레이아웃과 구조는 prototype/화면설계서-가이드.md 를 따른다. 
전달이 필요한 시점에만 PDF 로 빌드한다.

```bash
bash prototype/build-all.sh v0.2
```

docs 가 바뀌어서 화면설계서 버전을 올려야 한다면, 그건 절차 A 다. "화면설계서 버전 업데이트해줘"라고 하면 designspec-version-update 가 docs 를 먼저 맞추고 설계서를 다시 뽑는다.

**배포하고 다음 버전 라인을 연다.** 
배포 여부는 사람만 정한다. 배포한 뒤에는 그 버전을 동결하고 다음 버전 라인을 여는 형상 관리를 한다. 이게 절차 B 다.

```bash
bash scripts/release-cut.sh USER v0.2 v0.3
```

배포본을 불변으로 얼리고, 다음 라인을 열고, 버전 라벨을 안전하게 올리는 일을 스크립트가 한다. "vX 배포했고 다음 버전으로"라고 말해도 release-cut 스킬이 같은 일을 안내한다.

**마지막에 무엇을 왜 했는지 남긴다.** 
그날 한 일은 DEVLOG, 버전 차원의 변경은 HISTORY, 외부에 알릴 내용은 SHARE 에 적는다. 진척은 ROADMAP 에 갱신한다. 이렇게 남겨두면 다음 세션에서 맥락을 다시 설명하지 않아도 된다.

## AI와 일하는 방식

평범한 말로 시키면 된다. "사용자 콘솔에 닉네임 변경 화면 만들어줘. 정책이랑 검증 기준 맞춰서" 정도면 충분하다.

그러면 AI 가 docs 를 먼저 읽고, 그 말이 어떤 요건과 어떤 화면, 어떤 정책과 검증에 해당하는지 찾아낸다. <br>
그리고 "이건 닉네임 변경 요건(REQ-USER-0001)이고 사용자 정보 화면(SCR-USER-001)에 들어가요. <br>
닉네임 정책(POL-USER-0001)을 지켜야 하고 검증 케이스 세 개(TC-USER-0001~0003)로 확인해요. 맞나요?"처럼 되짚어 확인한 다음 작업한다. <br>
ID 를 꺼내는 쪽은 사람이 아니라 AI 다. ID 는 외우라고 있는 게 아니라, AI 가 정확히 가리키고 기록에 추적을 남기려고 쓰는 장치다. <br>
docs 를 먼저 읽는 건 behavior.md 에 규칙으로 박혀 있어서, 따로 시키지 않아도 그렇게 한다.

콕 집어 시키고 싶을 때만 번호가 필요하다. 머리로 기억하는 것이 아니라 docs/INDEX.md 에서 확인할 수 있다. <br>
모든 요건과 화면, 검증이 ID 와 함께 한 곳에 정리돼 있어서 거기서 보고 가리키면 된다.

경계는 단순하다. 
무엇을 왜 만들지 정하는 판단, 정책과 콘텐츠를 못 박는 일, 검증이 올린 빨간 항목을 어떻게 할지 정하는 결정, 그리고 배포를 누르는 일은 사람이 한다. <br>
초안을 만들고, 구멍을 탐지하고, 정합성을 검증하고, 반복 작업을 처리하는 일은 AI 가 한다. <br>
그래서 사람은 판단에 시간을 쓰고, 손이 많이 가는 일은 맡기게 된다.

## 막히면 어디를 보나

일하는 방식 전체가 궁금하면 rules/methodology/README.md 가 단일 진실이다. <br>
화면설계서를 어떻게 그리는지는 prototype/화면설계서-가이드.md 와 rules/methodology/designspec.md 에 있다. <br>
버전과 형상 관리에서 헷갈리면 rules/methodology/change-management.md 를 본다. <br>
셋업과 placeholder 치환을 실전으로 따라가려면 SETUP.md 가 가장 가깝다. <br>
무언가 어긋난 것 같을 때는 일단 `bash scripts/check-docs.sh` 를 돌려본다.

## 처음 시도하는 사람을 위하여

먼저 만들고 싶은 것을 말로 풀어 본다. "iOS 스크린캡처 앱 서비스를 구상 중이야" 정도면 된다. <br>그러면 AI 가 빈 곳을 되묻고, 그 답을 요건·정책·용어·화면·검증으로 나눠 docs 에 초안으로 적는다. <br>무엇을 왜 만드는지는 내가 정하고, 문서로 펼쳐내는 손은 AI 가 맡는다. 그 분담을 여기서 처음 겪는다. <br>
그 다음 `bash scripts/new-domain.sh USER 사용자콘솔` 로 도메인 하나를 만들어 보고, 출력되는 placeholder 목록을 훑으며 화면설계서가 어떤 자리들로 이뤄지는지 감을 잡는다. <br>마지막으로 "USER 도메인 검증 루프 돌려줘"라고 해서 검증 루프가 어떻게 도는지, 결과가 docs/REVIEW.md 에 어떻게 쌓이는지 확인해본다. <br>
이 세 단계를 진행해봄으로써 프로세스의 시작과 끝을 경험한 것이다.
