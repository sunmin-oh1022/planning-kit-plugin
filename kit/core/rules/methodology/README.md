# rules/methodology/ — 기획자 × AI 페어 작업 방법론

> '어떻게 일하는가'의 단일 진실. 매 세션 진입 시 CLAUDE.md → rules/behavior.md 를 통해 5대 원리가 자동 적용된다.
> 9개 기획 문서별 작성 칸·예시는 → [templates.md](./templates.md)
> 요건 200개·도메인 3개를 넘기 시작하면 → [indexing.md](./indexing.md)
> 화면설계서 제작 방법론(언제·어떤 순서로) → [designspec.md](./designspec.md)
> 산출물 버전 동기화·형상 관리(절차 A/B) → [change-management.md](./change-management.md)
> 기획 진척판(도메인×Phase) → [`../../ROADMAP.md`](../../ROADMAP.md)
>
> **반복 프로세스는 스킬로 호출한다** (`.claude/skills/`): `release-cut`(릴리스 컷) · `designspec-version-update`(버전 업데이트) · `spec-self-review`(셀프 검토) · `spec-verify-loop`(도메인/버전 검증 루프 — 7축 멀티에이전트 교차검증·적대적 환각 제거).

## 한 문장 요약
> **"AI에게 일을 시킨다"가 아니라 "AI가 잘 일할 수 있는 환경(규칙·맥락·검증·기억)을 미리 설계한다."**

사람 동료는 막히면 묻지만 AI는 묻지 않고 빈 곳을 그럴듯하게 메운다(환각). 그래서 기획자의 새 역할 = **'읽힐 문서'가 아니라 '실행될 문서'** 를 쓴다.

## 5대 원리 (모든 문서·기능에 항상 적용)
1. **단일 진실** — 한 사실은 한 곳에만. 같은 값이 두 문서에 보이면 한쪽은 ID 참조로.
2. **ID로 추적** — `REQ-### → SCR-### → TC-###`, 정책 `POL-###`, 플로우 `FLOW-###`.
3. **모든 상태** — 정상 외에 로딩·빈·에러·권한·오프라인. 적용 불가는 `N/A` 명시.
4. **Out of scope** — '이번엔 안 함' 명시. 좁힐수록 빠름.
5. **Given–When–Then** — '빠르게·자연스럽게·직관적으로' 금지. 숫자·동작으로.

> 셀프 점검 신호: 막연한 표현이 보이면 멈추고 숫자/동작으로 / 같은 값이 두 곳에 보이면 한쪽을 ID 참조로.
>
> 위 5대는 **기획** 원리. **코드 작성** 시 LLM 룰은 별도로 둔다 — 예: `rules/behavior.md` 에 Karpathy 4원칙(생각→단순함→외과적 변경→검증)을 흡수해 상보적으로 운용.

## 6 Phase (기능·버전마다 1→5 반복, Phase 0은 프로젝트당 1회)
| Phase | 이름 | 핵심 질문 | 산출물 |
| --- | --- | --- | --- |
| 0 | 환경 셋업 | 어떤 규칙 위에서 일하나 | 저장소·진입점·rules/·1초 검증 |
| 1 | 기획 문서 작성 | 무엇을·왜 만드나 | PRD · POL · glossary · REQ · SCR · TC |
| 2 | 셀프 검토 | 구멍·모순 없나 | AI 검토 결과 + 마감 체크 통과 (수동 1패스 `spec-self-review` / 도메인범위 멀티에이전트 교차검증 `spec-verify-loop`) |
| 3 | 핸드오프 | AI에 어떻게 넘기나 | 한 줄 작업 지시 |
| 4 | 구현·검증 루프 | 맞게 됐나 | 통과한 테스트 + 정합성 검증(`scripts/check-docs.sh` — 인덱스·추적 끊김 포함) + 실환경 확인 |
| 5 | 기록·반복 | 어떻게 기억하나 | 커밋 · DEVLOG · HISTORY · ROADMAP 진척 갱신 |

## 문서 4단 체계 (위→아래 = 넓은 맥락 → 구체 검증)
| 단계 | 문서 | 한 줄 |
| --- | --- | --- |
| ① 상시 브리프 | PRD · ROADMAP | 무엇을·왜·누구를 위해 / 어디까지 왔나 |
| ② 가드레일 | POL · glossary · _labels | 지킬 규칙·예외 / 표기·라벨 통일 (단일 진실) |
| ③ 가이드 | REQ · INDEX · IA · FLOW · SCR | 실행 지침 + 인덱스 + 상태 매트릭스 |
| ④ 검증·기록 | TC · DEVLOG · HISTORY | GWT로 증명 + 결정 보존 |

규모가 작으면 ①③④만으로도 충분. 정책·예외가 많을수록 ②의 비중↑. REQ 가 200개를 넘기 시작하면 [indexing.md](./indexing.md) 가 ③의 핵심이 됨.

## 기록 파일 역할 지도 (DEVLOG · HISTORY · SHARE · RELEASE · 설계서 revision)
> "이 변경을 어디에 적나"의 단일 진실. 독자(내부/외부) × 단위(일/버전/기능/릴리스)로 나뉜다.

| 파일 | 독자 | 단위 | 무엇을 | 여기 **안** 적는 것 → 어디로 |
| --- | --- | --- | --- | --- |
| `DEVLOG.md` | 내부(팀·AI) | 일자/작업 | 한 일·버그·왜 결정했나 | 버전 확정 변경 → `HISTORY` |
| `HISTORY.md` | 내부·다음세션 AI | 버전 | 프로젝트 차원 변경(도메인 횡단) | 산출물 화면 개정 → 설계서 revision · 외부 공지 → `SHARE` |
| `SHARE.md` | 외부(사용자·동료) | 기능 | 공유할 기능 변경·의도(비기술 언어) | 빌드·출시 운영 → `RELEASE` |
| `docs/RELEASE.md` | 외부·출시 운영 | 릴리스 | 출시 범위·빌드 메타·출시 체크리스트(ID 참조) | 변경 이력 자체 → `HISTORY` |
| 설계서 revision 페이지 | 외부·이해관계자 | 설계서 산출물 | 그 설계서의 화면 개정 이력 | 프로젝트 차원 변경 → `HISTORY` |

## 폴더 구조 (rules / docs 분리 — 메타 규칙 vs 산출물)
> 아래는 방법론 설명용 골격. 킷 **전체 폴더 트리의 권위는 루트 [`README.md`](../../README.md)**.
```
project/
├── CLAUDE.md (또는 CLAUDE.md)         ← 얇은 진입점 (200줄 이하)
├── rules/                             ← "어떻게 일하나" — 메타 규칙
│   ├── behavior.md · boundaries.md    (항상 @import)
│   ├── architecture.md · commands.md · domain.md · ui.md · ux.md  (작업별)
│   └── methodology/                   ← 이 폴더 — 기획·작업 방법론
├── scripts/                           ← 1초 검증·정합성 자동화
│   └── check-docs.sh                  (참조 경로·자동 로드 체인·테스트 한 번에)
└── docs/                              ← "무엇을 만드나" — 산출물 (평탄 구조)
    ├── README.md                              (진입 가이드 + 파일명 규칙 ★)
    ├── PRD.md · glossary.md · personas.md   (제품 정의·용어·페르소나)
    ├── POL.md                                 (정책)
    ├── REQ.md · INDEX.md · _labels.md        (요건·인덱스·라벨)
    ├── IA.md                                  (정보구조 — 메뉴↔화면 매핑)
    ├── TC.md                                  (Given–When–Then)
    ├── PRIVACY.md · RELEASE.md                (출시 운영 — 개인정보 처리방침·릴리스 노트)
    ├── screens/        SCR-### (★ 상태 매트릭스)
    ├── flows/          FLOW-### (사용자 플로우)
    └── domains/        {도메인}/REQ·POL·SCR·TC (REQ 200+ 시 분할)
```

> 파일명 규칙(약어/ID/일반 명사/시스템 4분류)은 [`docs/README.md`](../../docs/README.md) 가 단일 진실.

도구별 진입점: Claude → `CLAUDE.md`, Codex → `AGENTS.md`. 한 벌만 관리하려면 `ln -s CLAUDE.md AGENTS.md`.

## Phase 0 — 환경 셋업 체크리스트 (프로젝트당 1회)
실행용 체크박스 목록의 **단일 진실 = 저장소 루트 [`CHECKLIST.md`](../../CHECKLIST.md)**. 항목을 그대로 체크하며 진행하고, 완료 항목은 `[done]` 로 표시한다.

> 핵심 흐름만: 저장소·첫 커밋 → Core/App 분리 → 얇은 진입점(import + Rule Index) → rules/ 모듈(항상/작업별) → 가드레일(금지+대안+이유) → 1초 검증(`commands.md`)·정합성(`check-docs.sh`) → 사람/AI 경계 → DEVLOG·HISTORY·SHARE 생성.

## Phase 2 — 셀프 검토 프롬프트 (마감 전, 그대로 복사)
```
다음 기획 문서들을 읽고 점검해줘. 추측해서 채우지 말고,
실제 적혀 있지 않은 것은 '적혀 있지 않음'으로 표시해줘.

1. 정의되지 않은 용어 — glossary에 없는데 본문에 쓰인 단어
2. 문서 간 모순 — 같은 항목이 서로 다른 값/규칙으로 적힌 곳
3. 빠진 상태 — 정상 외 로딩·빈·에러·권한·오프라인 정의 여부
4. 빠진 범위 — Out of scope에 명시 안 된 모호한 영역
5. 검증 불가 표현 — '빠르게·자연스럽게·직관적으로' 같은 막연한 말
6. 빠진 비기능 — 성능·접근성·보안·다국어·데이터 보관/삭제
7. 추적 끊김 — REQ ↔ SCR ↔ TC 매핑이 빠진 항목

각 지적은 구체적 위치(파일·줄)와 함께 알려줘.
```

## 재사용 5가지 운영 패턴 (원리와 별개 — 실전 운영 노하우)
1. **맥락을 일감 옆에 둔다** — 규칙·맥락을 한 저장소에. 구두 지시 최소화.
2. **금지부터 정한다** — "하라"보다 "하지 마라". 이유까지.
3. **검증을 1초로** — 검증 가능한 부분을 떼어 AI가 스스로 증명 (`npm test`·`pytest -q`·`scripts/check-docs.sh` 류).
4. **사람/AI 경계 명문화** — 콘텐츠·디자인·확인 = 사람 / 구현·반복·검증 = AI.
5. **기억을 지속** — DEVLOG·HISTORY로 세션 간 맥락 복원.
